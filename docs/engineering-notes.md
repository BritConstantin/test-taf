# Interview preparation: ten decisions to defend

1. **Specification before implementation.** The [contract](../contracts/openapi.json) and [rules](suitability.md) propose observable behaviour where the ticket is silent. This enables a concrete product discussion. Rejected: building a reference API, which could make tests agree with invented implementation details. These tests need product agreement, not merely technical approval.

2. **Two-step name journey and arbitrary-ID resolution.** [Journey steps](../src/steps/ranking.ts) search and select the second candidate; [World resolution](../src/support/world.ts) expects provider `/v1/get`. This preserves ambiguity and avoids an undocumented town database. Rejected: first-result selection or treating a GeoNames ID as coordinates. Discuss how a frontend displays country/admin/timezone.

3. **One public runtime schema source.** [Ajv validation](../src/contracts/validate.ts) uses the actual OpenAPI component tree, retaining local `$ref` paths. OpenAPI 3.0.3 uses a supported schema subset, including Ajv's nullable support. [Validation checks](../test/validate.ts) validate the full document, static examples and negative samples. TypeScript interfaces describe validated data; they do not validate network JSON. Rejected: a parallel Zod schema that could drift independently.

4. **Independent, inspectable scoring oracles.** [Feature tables](../features/ranking.feature) and [seven manual examples](../src/provider/examples.ts) enumerate expected scores and reason codes. They are not an implementation of the ranking rules. Guard rules precede favourable rules, so selected contrasts are meaningful without requiring global monotonicity. Rejected: duplicating a formula in the test and reproducing the same mistake twice.

5. **Weather-only scope visible to consumers.** [Suitability rules](suitability.md) independently score all four activities using real daily fields. [Week assertions](../src/contracts/validate.ts) require limitation metadata and actual numeric weather facts. Surfing is intentionally a limited weather proxy; adding Marine API alone would not solve location applicability. Rejected: inferring waves from ordinary wind data or ski resorts from snow forecasts.

6. **A real HTTP dependency boundary.** [ProviderStub](../src/provider/stub.ts) listens on TCP and is reachable by an external process. It controls providers, never public API responses. Required parameter values are matched, while query/field order is ignored. Consumption and unmatched-request checks prevent fixtures from becoming decorative. Rejected: an in-process interceptor with no control over the SUT's own HTTP clients.

7. **Explicit clock protocol and calendar windows.** [Clock configuration](provider-control.md#required-future-sut-seams) freezes application time, not just runner time. [Fixtures](../src/provider/fixtures.ts) use explicit seven-date lists around Warsaw DST and opposite local dates. [Calendar scenarios](../features/ranking.feature) verify every returned date. Rejected: adding 86,400,000 milliseconds to local midnight or using fixed UTC offsets across DST.

8. **Small, honest lifecycle and failure model.** [World](../src/support/world.ts) owns scenario data and a stub instance. [Hooks](../src/support/hooks.ts) await readiness and close in finally; [harness probes](../test/harness.test.ts) exercise delayed-request cleanup and port reuse. Serial execution is a deliberate limit of the fixed-port/SUT setup. Rejected: parallel workers sharing a mutable provider fixture server or arbitrary sleeps for readiness.

9. **Separate transport from HTTP errors.** [ApiClient](../src/api/client.ts) returns status, headers, raw and unknown parsed body for any HTTP status. DNS/refusal/deadline failures throw a contextual TransportError preserving cause; invalid JSON remains inspectable. [Failure features](../features/provider-failures.feature) specify user-facing mappings and no downstream call after resolution failure. Rejected: throwing away error responses or letting a caught transport exception count as a pass.

10. **Green quality gates, explicitly red acceptance.** [Quality workflow](../.github/workflows/quality.yml) checks only work that can pass without a product. [Manual acceptance](../.github/workflows/acceptance.yml) runs real scenarios, fails normally and uploads reports. [Evidence](verification.md) distinguishes binding/harness checks from unexecuted business assertions. CommonJS compiled by `tsc` avoids runtime loader complexity; the exact Node/Cucumber/TypeScript versions were verified together. Rejected: a fake SUT, inverted exit code, retry-to-green or an acceptance badge implying product verification.
